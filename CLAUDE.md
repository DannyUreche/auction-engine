# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Spring Boot 4.2 / Java 21 REST API for auctions (PostgreSQL, Flyway, Spring Security + JWT, Lombok, springdoc Swagger).

## Running

- Start the DB first: `docker compose up -d` — Postgres is exposed on **port 5433** (not 5432), db/user/pass `auction_db`/`admin`/`password`.
- Use the Maven wrapper: `./mvnw spring-boot:run`, `./mvnw test` (on Windows PowerShell: `.\mvnw.cmd ...`). `JAVA_HOME` may not be set globally; on the author's machine a JDK is at `C:\Users\urech\.jdks\openjdk-27.0.1.0.3`.
- The JWT secret comes from `local.properties` in the project root (git-ignored, imported via `spring.config.import`) or the `JWT_SECRET` env var; the app won't start without it. See `local.properties.example`.
- `git push` from the agent shell fails ("terminal prompts disabled"): the user's GitHub login lives in VS Code's own auth, not in Git Credential Manager. Commit, then ask the user to push via the VS Code Source Control button.
- Tests are `@SpringBootTest` against the real Postgres — they fail if the docker container isn't running.
- Swagger UI: `http://localhost:8080/swagger-ui.html`. Public (no token): `/api/auth/**`, Swagger, `/error`, `GET /api/images/**`, `GET /api/events`, and read-only `GET /api/items`, `/api/items/**`, `/api/bids/**` — except `/api/items/my`, `/api/items/won`, `/api/bids/my`, which are declared authenticated *before* the public GET matchers in `SecurityConfig` (order matters). Everything else needs `Authorization: Bearer <jwt>` from `/api/auth/login`. In the frontend, `/` and `/items/:id` are public; `/sell` and `/account` are wrapped in `RequireAuth`.

## CI and browser tests

- Frontend unit tests: Vitest (`npm test`, `npm run test:coverage`), files `src/__tests__/*.test.js`, config in `vite.config.js` (`test:`); they cover plain logic modules (`api.js`, `i18n.jsx` `translate`, `pwa.js`, `errorReporting.js`) and stub browser globals with `vi.stubGlobal`. On Windows run them from a path with an uppercase drive letter (`D:\...`) - with `d:` Vitest loads itself twice and every file fails with "Cannot read properties of undefined (reading 'config')".
- Backend coverage: Maven profile `coverage` (JaCoCo) -> `target/site/jacoco/`. CI (`ci.yml`) runs `test -Pcoverage`, a separate `frontend` job runs Vitest with coverage, and both write the line coverage to the run summary.

- `.github/workflows/ci.yml` runs on every push/PR to `main`: job `backend` (`./mvnw -B test` against a `postgres:16` service on port 5433, dummy `JWT_SECRET`), then job `e2e` (packages and starts the jar, then Playwright).
- Playwright tests live in `frontend/e2e/` (`npm run test:e2e`, config `frontend/playwright.config.js`). They need the backend on 8080; Playwright starts Vite itself (or reuses a running one locally). Locally they use the installed Google Chrome (`channel: 'chrome'`), in CI the downloaded Chromium. Each run registers a fresh `e2e_*` user.

## Load test

- `load-test/bid-storm.mjs` (Node, no deps): 200 bidders x 5 auctions x 30 s + 50 SSE listeners against the LOCAL backend (refuses other hosts without `--allow-remote`), then checks consistency; reports in `load-test/reports/` (git-ignored). Start the backend with `APP_RATE_LIMIT_AUTH_PER_MINUTE=100000` or registrations get 429. Results and conclusions in `load-test/README.md` (data stayed consistent; the laptop CPU was the limit). `BidService.placeBid` rejects a too-low bid from a lock-free price read (`ItemRepository.currentPrice`) before taking the row lock.

## Deployment (Render)

- `render.yaml` (Blueprint) defines only the Docker web service `auction-engine`, region Frankfurt. The production DB is on **Neon** (free, doesn't expire; Frankfurt), not Render: env vars `DATABASE_URL` (JDBC form, `jdbc:postgresql://<host>/neondb?sslmode=require`, use the *direct* host, not `-pooler`, because of Flyway), `DATABASE_USERNAME`, `DATABASE_PASSWORD` are `sync: false` and set in the Render dashboard. `JWT_SECRET` is generated; `PORT` is set by Render. Locally all of these fall back to the defaults in `application.properties` (Docker Postgres on 5433).
- `Dockerfile` builds the React app, copies `frontend/dist` into `src/main/resources/static`, and packages one Spring Boot jar (tests skipped in Docker — they need Postgres). - Keep-alive: `.github/workflows/keep-alive.yml` pings the public `GET /api/health` (checks the DB with `SELECT 1` via `DatabaseProbe`) every 10 minutes so the free Render instance doesn't spin down (GitHub pauses scheduled workflows after 60 days without repo activity).
- Render deploys automatically on every push to `main`. Live URL: https://auction-engine.onrender.com (first deployed 2026-11-23). The production DB is separate from the local one and started empty.

## Database

- Schema is owned by Flyway (`src/main/resources/db/migration/V<n>__*.sql`); Hibernate runs with `ddl-auto=validate`. Any entity change needs a new migration with the next version number — never edit an existing migration.

## Conventions

- Write **code comments and commit messages in English** (owner's request from 2026-11-24; older code still has Romanian comments, no need to translate them). **User-facing text** (UI, error messages returned by the API) stays **Romanian without diacritics**.
- Error monitoring (self-hosted, V28 `app_errors`): `GlobalExceptionHandler.handleUnexpected` catches any other exception -> 500 `{"eroare"}` and records it via `ErrorMonitorService.recordServerError` (REQUIRES_NEW, never throws); Spring `ErrorResponse` exceptions (404, 405, ...) keep their status and aren't recorded; client disconnects are rethrown. Browsers report JS errors to public `POST /api/client-errors` (20/min per IP; `src/errorReporting.js` + `ErrorBoundary` in `main.jsx`). Rows are grouped by a SHA-256 fingerprint (source + message + first stack line) with an `occurrences` counter, max 300 open. Admin tab "Erori": `GET /api/admin/errors`, `POST /api/admin/errors/{id}/resolve`, `DELETE /api/admin/errors/resolved`.
- Business-rule violations throw `IllegalArgumentException`; `GlobalExceptionHandler` turns them into HTTP 400 with body `{"eroare": "<message>"}`. Request DTOs use Bean Validation (`@Valid` + `jakarta.validation` annotations with Romanian messages), also returned as 400 `{"eroare": ...}`. Missing/invalid JWT gives 401 in the same format.
- The current user comes from the JWT: take `Authentication authentication` in the controller and pass `authentication.getName()` (username) to the service. Never accept user ids (e.g. `bidderId`, `sellerId`) in request bodies.
- Solo project: committing directly to `main` is fine (only when asked).

## Known gotchas

- `AuctionScheduler` closes expired auctions every 15 s and sets `Item.winner` from the highest bid. Its jobs re-read items with a row lock (`entityManager.refresh(item, PESSIMISTIC_WRITE)`) before saving, otherwise a save from a stale read overwrites a bid's new price.
- Item photos: up to `Item.MAX_IMAGES` (5) per item. Bytes live in `item_images` (bytea, V9) because Render's free plan has no persistent disk; the ordered list is `item_photos` (V12: `item_id`, `position`, `image_filename`), mapped as an `@ElementCollection` `Item.imageFilenames` with `@OrderColumn` (position 0 = main photo shown on cards) and `@Fetch(SUBSELECT)`. JSON exposes `imageUrls` (all) and `imageUrl` (main). Seller-only endpoints: `POST /api/items/{id}/images` (multipart field `image`, max 5 MB, type detected from magic bytes in `ImageStorageService`), `DELETE /api/items/{id}/images/{filename}`, `POST /api/items/{id}/images/{filename}/main`. Delete a photo from the list (and flush) *before* deleting its `item_images` row (FK). `GET /api/images/**` is public because `<img>` can't send the JWT.
- Watchlist ("Urmaresc"): `watched_items` (V13, unique per user+item, `ON DELETE CASCADE` on the item). `GET /api/items/watched` (declared authenticated before the public GET matchers), `POST`/`DELETE /api/items/{id}/watch` (idempotent; can't watch your own item). Frontend: `WatchlistProvider`/`useWatchlist`/`WatchButton` in `frontend/src/watchlist.jsx` (wraps `App` in `main.jsx`); it shows toast notifications for live `bid`/`closed` events on watched items (skipped on that item's own page and for your own bids).
- Live updates: `BidService` and `AuctionScheduler` publish an `AuctionEvent` (`bid` / `closed`); `AuctionEventService` forwards it via `@TransactionalEventListener(AFTER_COMMIT)` to all `SseEmitter`s from `GET /api/events` (public, Server-Sent Events, 25s heartbeat). Frontend subscribes with `useAuctionEvents` in `frontend/src/events.jsx`, which shares ONE `EventSource` per tab between all subscribers (browsers cap open HTTP/1.1 connections per host); polling (30s) remains only as a fallback.
- Notifications: `notifications` (V15, user FK `ON DELETE CASCADE`), created by `NotificationService.notify` from `BidService.saveBid` (OUTBID for the previous leader, NEW_BID for the seller) and `AuctionScheduler.closeAuction` (WON / SOLD / UNSOLD). `GET /api/notifications` (unread + last 30), `POST /api/notifications/read-all`. Each notify also publishes `AuctionEvent.notification(username)` (SSE type `notification`, no text - the client refetches) and the `Notification` entity itself as a Spring event (for email). Frontend: `NotificationBell` in the header.
- Email: `spring-boot-starter-mail`, SMTP from env `MAIL_HOST/MAIL_PORT/MAIL_USERNAME/MAIL_PASSWORD/MAIL_FROM` (e.g. Brevo `smtp-relay.brevo.com:587`), links use `APP_BASE_URL`. `EmailService` only logs when `MAIL_HOST` is blank (local, tests, Render until configured) and never throws. `EmailNotificationListener` (`@Async` + `@TransactionalEventListener(AFTER_COMMIT)`, `@EnableAsync` on the app) emails OUTBID / WON / SOLD notifications.
- Rate limiting: `AuthRateLimitFilter` allows `app.rate-limit.auth-per-minute` (default 10) POSTs per client IP per sliding minute on `/api/auth/login|register|forgot-password` (IP = first `X-Forwarded-For` value, since Render is behind a proxy); over the limit -> 429 + `Retry-After` + `{"eroare": ...}`. In-memory, per instance. Tests raise the limit in `src/test/resources/config/application.properties` (loaded on top of the main file).
- Password reset: `POST /api/auth/forgot-password` (same response whether the email exists or not) emails `APP_BASE_URL/reset-password?token=...`; only the SHA-256 of the token is stored (`password_reset_tokens`, V16), valid 30 min, single use; `POST /api/auth/reset-password`. React pages `/forgot-password`, `/reset-password` (also in `SpaController`).
- Reviews: `reviews` (V17, one per item+author, rating 1-5). `POST /api/items/{id}/reviews` only by the seller or the winner of a sold item; `GET` is public. The public profile includes `rating` (average, count) and the last 20 received reviews (`ReviewService.ReviewDto`, no emails). Demo data adds reviews for sold items.
- Chat: `messages` (V18). `GET/POST /api/items/{id}/messages` only for the seller and winner of a sold item (GET declared authenticated before the public matchers). Sending publishes `AuctionEvent.message(itemId, recipient)` (SSE type `message`, no text) and a MESSAGE notification. Frontend `ChatBox` on the item page. Read receipts (V38 `messages.read_at`, old rows = read): `POST .../messages/read` marks the other participant's messages read (bulk JPQL update, `clearAutomatically`) and publishes SSE `read` to the sender; the `ChatBox` calls it while the chat is visible and shows ✓ / ✓✓ + "Citit". Typing: `POST .../messages/typing` publishes SSE `typing` to the other participant (max once per 2 s per user and chat, nothing stored); the bubble with bouncing dots disappears after 4 s. New SSE types must also be added to the list in `events.jsx`.
- User objects nested in items/bids (`seller`, `winner`, `bidder`) hide `email` via `@JsonIgnoreProperties`. Emails are exposed only by `/api/users/me` and by `GET /api/items/{id}/contact` (authenticated, declared before the public GET matchers): after a sale, the seller gets the winner's email and vice versa, nobody else. Public seller profile: `GET /api/users/{username}/profile` (permitAll, no email; active + sold items), React route `/users/:username` (also in `SpaController`).
- Categories: fixed `Category` enum (stored as string, V11, default `ALTELE`), listed publicly by `GET /api/categories`; frontend loads them once via `useCategories()` in `frontend/src/categories.js`. Filtering/sorting/paging on the home page is server-side: public `GET /api/items/search?q=&cat=&min=&max=&type=&sort=&page=&size=` (`ItemSearchService`, JPA Criteria; max 48 per page) returns `{items, total, page, size, totalPages, categoryCounts, allCategories}` (counts ignore the category filter). Home loads 12 per page with "Incarca mai multe", debounces text/price input 300 ms and on live events reloads all loaded pages; the hero carousel uses `search?size=10`. `/api/items/active` still exists (unpaged); filter state lives in local React state and is mirrored to the URL (`?cat=&q=&min=&max=&type=&sort=`; `type` = `buy`/`dutch`/`today`/`soon`, see `TYPES` + `matchesType` in `Home.jsx`; the filters are one highlighted panel with removable pills for the active filters) — don't drive inputs directly from `useSearchParams` (React Router 8 updates the URL in a transition and rapid updates get lost).
- Editing: `PUT /api/items/{id}` (seller only, only while active and with zero bids; same fields as create minus duration, `currentPrice` reset to `startPrice`, `endTime` unchanged). Frontend: inline `EditItemForm` on the item page.
- Concurrency: every path that changes an item's price locks the row first - `ItemRepository.findByIdForUpdate` (PESSIMISTIC_WRITE, `SELECT ... FOR UPDATE`) in `BidService.findItem` (bid, auto-bid, buy now) and `OfferService.respond`; `AuctionScheduler.closeAuction` flushes, re-reads the item with a lock and returns if it is already closed. `ConcurrentBidTest` (not @Transactional, real threads) proves 8 simultaneous identical bids give exactly one accepted bid. New price-changing code must use the locked read.
- Bidding rules live in `BidRules`: tiered minimum increment (<100: 1, <1000: 5, <10000: 10, else 50 RON; exposed as `Item.minimumBid`), anti-sniping (a bid with <2 min left moves `endTime` to now + 2 min), optional `buyNowPrice` (V10) — `POST /api/items/{id}/buy-now` records a bid at that price and closes the auction via `AuctionScheduler.closeAuction`; available only while `currentPrice < buyNowPrice` (`Item.buyNowAvailable`). Proxy bidding: `auto_bids` (V14) + `PUT/GET/DELETE /api/items/{id}/auto-bid` (GET is authenticated, max is private). `BidService.resolveAutoBids` runs after every manual bid and every auto-bid change: while some other user's auto-bid can beat the leader, it bids `min(its max, minimumNextBid(leader's max or current price))`; auto bids are saved with `bids.automatic = true`. Anti-sniping is applied inside `saveBid`, so it covers auto bids too.
- Admins: usernames listed in `app.admin-usernames` (env `ADMIN_USERNAMES`, comma-separated; locally via `local.properties`) get `ROLE_ADMIN` in `CustomUserDetailsService` (via `AdminAccess`). `/api/admin/**` is `hasRole("ADMIN")` (403 JSON otherwise); `/api/users/me` returns `admin: true/false` and the frontend shows `/admin` only then. Admin can close an auction now (reuses `AuctionScheduler.closeAuction`) and delete items (bids deleted first via `BidRepository.deleteAllForItem`, then the item, then its photos). No user deletion on purpose. Admin charts: `GET /api/admin/charts` (bids per day for the last 14 days incl. empty days, sales by category, top 5 sellers) drawn by `components/AdminCharts.jsx` (plain SVG/CSS, single hue, hover tooltips). Demo data: `DemoDataService` (`GET/POST/DELETE /api/admin/demo-data`) creates users `demo_*` (`@demo.licitatii.live`, random password), 16 hand-made items (some sold) plus the `DemoCatalog` (10 per category: classic auctions with buy-now and bids, one Dutch and one scheduled each) with Java2D photos (`DemoImagePainter` draws a studio shot of a per-listing shape/color: full view, dark angled view, close-up) and back-dated bids; delete removes exactly those. The Docker runtime image installs `fontconfig ttf-dejavu` for this (Alpine has no fonts).
- Scheduled and Dutch auctions (V19): `Item.startTime` (null = open since creation; `started` in JSON), `startNotified` (false until the STARTED notifications went to the seller and watchers), `auctionType` ENGLISH/DUTCH, `floorPrice`, `priceDrop`. `endTime` = start + duration. Before the start no bids/buy-now ("Licitatia nu a inceput inca!"). DUTCH: no bids or auto-bids, only `POST /buy-now` at `Item.dutchPriceAt(now)` (start price minus one drop per full minute since `startTime`, never below the floor; same formula in frontend `dutchPrice()` in `api.js`), can't be edited. `AuctionScheduler.updateRunningAuctions` (every 15 s) sends STARTED notifications and refreshes Dutch `currentPrice`, publishing `AuctionEvent.update` (SSE type `update`).
- Wallet (V20): `users.balance` (default 10000 RON, `@JsonIgnore`), `wallet_transactions` (TOP_UP/PURCHASE/SALE). `WalletService`: available = balance - reserved, reserved = current price of active ENGLISH items the user currently leads (`ItemRepository.reservedBy`). `checkFunds` before every bid/buy-now (auto-bids are capped at the available amount in `resolveAutoBids`); `settle(item)` in `AuctionScheduler.closeAuction` moves the money winner -> seller. `GET /api/wallet`, `POST /api/wallet/top-up` (test credits, max 5000 at once). Frontend: `useWallet(user)` (`wallet.js`), `WalletPanel` (account tab `?tab=wallet`), `WalletChip` in the header.
- Public Q&A (V21 `questions`): `GET/POST /api/items/{id}/questions` (GET public), `POST /api/items/{id}/questions/{qid}/answer` (seller only, once). The seller can't ask on their own item. Notifications QUESTION (to the seller) and ANSWER (to the asker). Frontend `Questions` card on the item page.
- Reports and blocking (V22): `POST /api/items/{id}/report` (reason enum `Report.Reason`, one per user+item, not on your own item). Admin: `GET /api/admin/reports`, `POST /api/admin/reports/{id}/dismiss`, `POST /api/admin/users/{id}/block|unblock` (admins can't be blocked). Blocked users: `CustomUserDetailsService` sets `enabled=false`, `JwtAuthenticationFilter` ignores their tokens, login says "Contul tau a fost blocat...".
- Email verification (V23): `users.email_verified` (existing users TRUE). Registration needs confirmation only when mail is configured (`EmailService.isConfigured()`); then `/register` returns `verificationRequired: true` and the frontend doesn't auto-login. Token = random, only its SHA-256 stored (`email_verification_tokens`), valid 48 h; `POST /api/auth/verify-email`, `POST /api/auth/resend-verification` (same answer whether the email exists or not, rate-limited). React page `/verify-email` (also in `SpaController`); unverified login shows a resend form.
- Account data (`AccountService`): `GET /api/users/me/export` (JSON with everything about the user, Romanian keys) and `DELETE /api/users/me` with body `{confirm: <username>}`. Deletion anonymizes: username/email become `sters_<id>`, random password, `blocked=true`; watchlist, auto-bids, notifications, push subscriptions and tokens are deleted; active items without bids are deleted; refused while the user leads an auction or sells an item that has bids. Frontend: account tab `?tab=settings` (`AccountSettings.jsx`).
- Live room (V25): `LiveRoomService` keeps presence in memory: each item page sends `POST /api/items/{id}/presence {session}` every 15 s (public; `session` = random per-tab id in sessionStorage) and `presence/leave` via `sendBeacon`; returns `viewers` (heartbeats younger than 45 s). The first heartbeat of a tab increments `items.view_count` (not for the seller; `@JsonIgnore`, used by seller statistics). Public live chat `live_comments`: `GET /api/items/{id}/comments` (public, last 50), `POST` (authenticated, active items only, 1 message per 3 s per user) publishes SSE type `comment`. Frontend `LiveRoom` card on the item page; live bids float up with `animate-rise`.
- County and delivery (V27, V29): `items.county` (V29 renamed V27's free-text `city` and mapped cities to counties) is one of the 41 counties + Bucuresti in `Counties.ALL` (frontend copy `src/counties.js`; `Counties.canonical` accepts any case/diacritics/hyphens and rejects other names), optional. `items.delivery` (`Delivery` COURIER/PICKUP/BOTH, default BOTH). Search filter `county`; public `GET /api/items/counties` returns all 42 counties with their active-auction counts (also 0). Frontend `LocationFields` (county select + delivery buttons) in the sell and edit forms; the card shows the county, the item page "jud. X · livrare". Demo data picks random counties.
- Reputation badges (`BadgeService`, computed, nothing stored): TRUSTED_SELLER (>=5 sales, rating >=4.5), ACTIVE_SELLER (>=10 listed), COLLECTOR (>=3 won), PASSIONATE_BIDDER (>=50 bids), FIRST_BIDDER (first bid on >=5 items), VETERAN (account >=1 year). In the public profile (`badges`) and `GET /api/users/{username}/badges` (public); frontend `Badges` (cards on `/users/:username`, compact pills next to the seller on the item page).
- Seller statistics: `GET /api/users/me/seller-stats` (`SellerStatsService`): per item views (`view_count`), bids, distinct bidders, watchers; totals incl. revenue (sold items) and rating; bids per day on the user's items for 14 days. `Item.viewCount` is `insertable/updatable = false` - only the JPQL UPDATE in `LiveRoomService` writes it. - Saved alerts (V26 `saved_alerts`): `GET/POST /api/alerts`, `DELETE /api/alerts/{id}` (own; max 10; at least one of query/category/minPrice/maxPrice). `AlertService.auctionOpened(item)` runs when an item is created already open (`ItemController.createItem`) and when a scheduled one starts (`AuctionScheduler`), and sends one `ALERT` notification per matching user (not the seller, not blocked users). Frontend: "Salveaza ca alerta" in the home filter panel (logged in, with text/category/price filters), account tab `?tab=alerts` (`AlertsPanel`).
